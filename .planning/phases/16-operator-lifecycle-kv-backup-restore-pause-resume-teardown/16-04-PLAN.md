<objective>
Stage A's operator gate: run `kv backup` and `kv restore --dry-run` against the real AWS
account once, with real credentials, and confirm the artifact is what the design promised.

Purpose: everything in 16-01 through 16-03 is proven against in-memory fakes. The failure modes
that fakes cannot surface are exactly the ones that matter — a table whose live row shapes
differ from the entity files, an unexpectedly large ledger, a terragrunt output that will not
resolve from the operator's shell, an IAM permission the operator's SSO profile lacks. The
ROADMAP makes this a gate: the destroy stage is deferred until Stage A has round-tripped once
against real data.

Output: a recorded, verified backup artifact on the operator's disk and a SUMMARY capturing the
measured ledger size, elapsed time, per-table row counts, and the dry-run destination
resolution.
</objective>

  <what-built>
    `kv backup` writes one timestamped zip holding all three DynamoDB tables as JSONL, the full
    S3 transcript ledger as a key-preserving object tree, the external inventory (VoIP.ms DIDs,
    NAT EIP, non-secret SSM parameters), and a manifest carrying a SHA-256 per file. Verification
    is on by default and re-opens the finished zip to re-check every digest and row count.
  </what-built>
  <how-to-verify>
    1. Build the CLI: `go -C kv build -o bin/kv ./cmd/kv`
    2. Confirm the operator AWS profile is live: `aws sts get-caller-identity --profile klanker-application`
    3. Measure the ledger ahead of time so the artifact size is not a surprise:
       `aws s3 ls --summarize --recursive s3://$(kv/bin/kv --help >/dev/null; cd infra/terraform/live/site/region/us-east-1/ledger && terragrunt output -raw bucket_name)`
       Record the object count and total size.
    4. Run the backup: `kv/bin/kv backup --out ./backups`
    5. Confirm the command reported: the artifact path, its size, elapsed wall time, per-table
       row counts, the ledger object count and byte total, and a closing block naming
       transcripts and user email addresses, stating the file is unencrypted, and stating it may
       be the only remaining copy.
    6. Confirm verification ran (it is on by default) and reported no mismatch.
    7. Independently spot-check the artifact without kv:
       `unzip -l ./backups/kmv-backup-*.zip | head -40` — confirm `manifest.json`, three
       `dynamodb/*.jsonl` entries, `ledger/` entries, and the three `external/` entries are
       present.
       `unzip -p ./backups/kmv-backup-*.zip manifest.json | head -60` — confirm the git SHA,
       account id, region, kv version, resolved table names, resolved bucket name, and row
       counts look right.
    8. Confirm the row counts in the manifest are plausible against what you know is in the
       tables — in particular that `kmv-auth-electro` carries your access codes and tiers and
       `kmv-voice-usage` carries usage and the kill-switch control row.
    9. Confirm `git status --porcelain` shows nothing under `backups/` — the ignore entry works.
    10. Re-run verification alone against the same file to confirm it is repeatable:
        `kv/bin/kv backup --out ./backups` a second time is NOT what to do here; instead confirm
        step 6's verification output was explicit about what it checked.

    Report back: the artifact size, the elapsed time, whether the size warning fired, the three
    row counts, the ledger object count, and anything the command printed that surprised you.
  </how-to-verify>

  <what-built>
    `kv restore <zip> --dry-run` re-verifies the archive, resolves every write destination from

  </what-built>
  <how-to-verify>
    1. Run: `kv/bin/kv restore ./backups/kmv-backup-<stamp>.zip --dry-run`
    2. Confirm the report shows two distinctly labelled blocks: the manifest's recorded provenance
       (git SHA, account id, recorded table names, recorded bucket) and the live-resolved
       destinations (resolved table names, resolved bucket). On a stack that has not been
       destroyed these will match — that is expected, and the point is that they are shown
       separately and sourced separately.
    3. Confirm each table shows a write count and a skipped count broken out by reason, and that
       `kmv-voice-usage` shows a non-zero concurrency-lease skip count if any session has run
       recently.

    5. Confirm a DRY RUN banner is present and that no write occurred: re-run
       `kv/bin/kv backup --out ./backups` is NOT the check — instead confirm via the AWS console

       that the item count is unchanged from before the dry run (allowing for normal drift if the
       service is live).
    6. Deliberately corrupt a copy of the artifact and confirm the refusal path:
       `cp ./backups/kmv-backup-<stamp>.zip /tmp/corrupt.zip`, flip a byte inside it with any
       editor or `printf` seek, then run `kv/bin/kv restore /tmp/corrupt.zip --dry-run` and
       confirm it exits non-zero naming the failing entry. Delete `/tmp/corrupt.zip` afterwards.

  </how-to-verify>

    - CLI: per-table write counts and per-reason skip counts are printed for all three tables
    - Behavior: DynamoDB item counts are unchanged after the dry run
    - Behavior: `kv restore` on a byte-corrupted copy of the artifact exits non-zero and names the failing entry path
    - Recorded: the SUMMARY states whether the ROADMAP's Stage-A gate ("round-tripped once against real data") is satisfied
