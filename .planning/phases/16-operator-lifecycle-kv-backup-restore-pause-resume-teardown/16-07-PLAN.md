<objective>
Close the two real hazards of the pause stage in code: the Application Auto Scaling
apply-ordering race, and the in-flight session drain.

Purpose: `aws_appautoscaling_target` declares `depends_on = [aws_ecs_service.service]`, so a
pause apply zeroes `desired_count` first and lowers `min_capacity` second. In that window
Application Auto Scaling can scale back out to MinCapacity, leaving a service pinned at one task
that terraform believes is at zero — a pause that reports success and did not happen. The window
is short and the evaluation cadence is roughly a minute, so it usually will not fire. "Usually"
is not an acceptable property for an operator tool, so verification closes it by issuing
`update-service --desired-count 0` itself. Separately, a pause issued mid-call has to wait on
task-scale-in protection, and waiting silently is indistinguishable from hanging.

Output: `kv/internal/app/cmd/lifecycle_ecs.go` and `lifecycle_alb.go` with their interfaces, the
drain-and-correct loop, the in-flight session reporter, the resume health wait, and tests
driving each hazard path against fakes.
</objective>

    marked line when a correction fires so a corrected pause is never silently indistinguishable

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| kv process → ECS control plane | kv issues a service mutation (`update-service`) outside the terraform apply that CI just ran |
| Application Auto Scaling → ECS services | an AWS-side controller can independently change capacity in the window this plan exists to close |
| live voice sessions → the drain decision | real users are on calls while capacity is being removed |
| ALB target health → the resume success claim | the only external evidence that the stack actually came back |
