<objective>
Give the operator per-call telephony analytics before the three phone-game DIDs
(725-404-3234 / 3283 / 8283) go out to a large group: ONE structured, greppable event line
per call emitted by the telephony controller at teardown, and a `kv telephony stats`
command that turns those lines into a per-DID summary via CloudWatch Logs Insights.

Purpose: today "how many people are calling each number, are they getting through the code
entry, and where do they give up?" is only answerable by hand-diving CloudWatch. The event
line makes it a query; the CLI makes it a one-liner during the event.

Output: a new `telephony/call_event.py` builder/emitter, two D-05e-safe read-only views on
`GateProcessor`, first-wins outcome recording threaded through the controller's existing
resolution sites, and a new `kv telephony stats` subcommand with offline-tested aggregation.
</objective>

- **D-01 — Exactly ONE line per call, at the single teardown seam.** Emit at the place every
  call already funnels through (`_close_active_call`, the method that already logs
  `_close_active_call: channel=... reason=...`). Never lost to an early hangup path, never
  emitted twice.
- **D-02 — Structured, greppable, single-line JSON with a stable marker prefix:**
  `game_call_event {"call_id": ..., "dialed_did": ..., "outcome": ..., ...}`.
- **D-03 — Field set (counts and timings ONLY), exactly these nine:** `call_id`,
  `dialed_did` (empty string if unresolved), `caller_id` (already logged today at
  `on_stasis_start` — no new exposure), `otp_only` (bool), `outcome`, `digits_entered`
  (count of DTMF digits received pre-unlock — count only), `words_heard` (count of STT
  tokens accumulated pre-unlock — count only), `seconds_to_outcome` (answer →
  unlock/announcement/fail, 1-decimal float), `duration_seconds` (answer → teardown,
  1-decimal float).
- **D-04 — Outcome labels:** `announcement_code`, `announcement_words`,
  `concierge_unlock_dtmf`, `concierge_unlock_passphrase`, `gate_timeout`, `early_hangup`
  (caller hung up pre-unlock), `error` (pipeline/teardown error path). Derive from state the
  code already tracks; prefer reusing existing state over inventing new state.
- **D-05 — D-05e REDACTION IS NON-NEGOTIABLE.** Never the DTMF digits themselves, never
  heard or matched words, never code values, never which game's code was wrong. Counts,
  outcome labels, and timings only. The existing opt-in `gate_debug_log_heard` fail-path
  plumbing is UNCHANGED by this task — do not touch it.
- **D-06 — Concierge (non-game) calls emit the same event too.** Volume analytics must cover
  all five DIDs, not just the games.
- **D-07 — `kv telephony stats`** is a new subcommand under the existing `kv telephony` tree,
  backed by CloudWatch Logs Insights via aws-sdk-go-v2, using the same SSO/env credential
  path every other kv command uses.
- **D-08 — Log group + flags.** Default log group
  `/ecs/telephony-edge-telephony-edge-use1-kmv` (confirmed against
  `infra/terraform/modules/ecs-task/v1.0.0/main.tf`'s `awslogs-group` =
  `/ecs/${container.name}-${family}`), exposed as a flag with that default. Flags:
  `--since` duration (default 24h), optional `--did` filter.
- **D-09 — Output.** Per-DID rows (total calls, outcome breakdown, median/max
  `seconds_to_outcome`, median duration, distinct-caller COUNT) plus a totals row, in the
  plain aligned `tabwriter` style `kv telephony list` already uses. `--json` dumps the raw
  aggregation. NEVER print raw caller numbers in the table, and NEVER include them in
  `--json` either — omit them entirely (the operator can go to raw logs for specifics).
- **D-10 — Out of scope.** No capacity/concurrency changes. No studio panel. No CloudWatch
  dashboards / custom metrics / EMF. No changes to `gate_debug_log_heard` or the transcript
  ledger.

**Claude's Discretion (CONTEXT grants this explicitly; recording the calls made here):**

- Marker spelling is `game_call_event` exactly as CONTEXT's own example wrote it.
- The `require_gate=False` escape hatch (test/dev-only, never production) has no gate and
  therefore no gate-derived outcome. It gets the label `ungated_grant` — an eighth label
  that exists ONLY so that dev path still satisfies D-01's "one line per call". Production
  never emits it.
- A quota rejection discovered right after unlock, and a quota rejection on the ungated
  path, both map to `error` — they are neither a window timeout nor a successful factor.
- The announcement outcome is stamped when the TRIGGER fires (the caller got through), not
  after the OTP fetch succeeds. A later OTP-fetch failure still reads as
  `announcement_code`/`announcement_words`, which is exactly the "did they get through the
  code entry" signal the operator asked for; the fetch failure is already logged separately.
- Aggregation is client-side in Go over a filtered Insights result set (a few hundred calls
  — favor simple and robust over a clever `stats` query), which is the split CONTEXT left
  open.
